# 建模方法论

这份文档记录**为什么这样建模**。代码会变，方法论不会。它也是答辩和评审时的依据。

---

## 1. 抽象层级的选择

### 1.1 建模阶梯

行业标准的抽象层级，从快到慢：

| 层级 | 方法 | 单次耗时 | 可达精度 | 建造成本 |
|---|---|---|---|---|
| L0 | 电子表格 / 解析式 | 瞬时 | 带宽 ±30~50% | 小时~天 |
| L1 | 排队论 / 运算分析 | 瞬时 | 均值延迟 ±10~30%（需校准） | 天~周 |
| L2 | 网络演算 / 实时演算 | 瞬时（闭式） | **安全上界**，常悲观 3~10 倍 | 周 |
| L3 | TLM-LT（松耦合时序） | 10~100× RTL | 功能正确，**争用建模差** | 周~月 |
| L4 | **TLM-AT（近似时序）** | ~1~10 MIPS | 若瓶颈已建模，吞吐可达 RTL 的 ±10~20% | 月 |
| L5 | 周期精确 | ~10~1000 KIPS | 建模范围内 ±数 % | 月~年 |
| L6 | RTL / 仿真器 | — | 该 RTL 的真值 | — |

### 1.2 本项目的选择

**主力在 L4（近似时序的交易级），L0/L1 作为前筛，L2 留作 Stage 3 的第三类答案。**

关键依据（来自研究）：**存储子系统与互联的吞吐/延迟分析必须用 AT 或更低层级，LT 不够。** LT 每事务只有两个时序点（请求/响应），无法独立延迟各个相位，因此建模不了仲裁与流水；AT 有四个时序点（BEGIN_REQ / END_REQ / BEGIN_RESP / END_RESP），每个相位可以独立延迟——这正是表达「仲裁等待」和「响应排队」所需的自由度。

本项目用 DES 实现 AT 语义，不依赖 SystemC。

### 1.3 为什么不到 L5（周期精确）

因为**问题不在那个尺度上**。本工具回答「架构够不够、瓶颈在哪、什么条件会失效」，这些答案在 AT 层级就已经收敛。周期精确会把成本提高一到两个数量级，而不会改变立项决策。

需要 L5 的场景是「时序能不能收敛」——那是 RTL 与 STA 的职责，不是架构探索的职责。

## 2. 三个互相冲突的学派，及本项目的处理

这是研究里最诚实的发现：这个领域**没有统一方法论**，三个学派互相很少引用，结论会打架。

| 学派 | 主张 | 代价 | 代表 |
|---|---|---|---|
| **保真派** | 用你能负担的最高保真度建模，低保真会给错误答案 | 覆盖率低 | Hennessy-Patterson 脉络 |
| **统计派** | 故意接受单点 5~7% 误差，换取 100~1000× 采样覆盖；**Pareto 前沿的排序对单点偏差是稳健的** | 单点数字不可信 | Harvard/Brooks、Polimi/MULTICUBE |
| **最坏情况派** | 拒绝概率，要**保证**的界 | 界常悲观 3~10 倍 | 网络演算 / 实时演算 |

**本项目的处理：同一个模型，输出三类答案。**

| 答案类型 | 用途 | 实现 | 阶段 |
|---|---|---|---|
| **标称值** | 优化、容量规划 | DES 仿真 | 1 |
| **统计边界** | 置信区间、敏感性 | 多次随机种子 + 方差分解 | 3 |
| **最坏情况保证** | 实时外设的延迟上界 | 网络演算 / 实时演算 | 3 |

**为什么不选一个**：实时外设要的是**界**，性能优化要的是**标称值**。同一个架构问题，两类消费者的正确答案不同。强行统一会牺牲其中一方。

## 3. 三条红线（会让结论失效的坑）

### 3.1 Little's Law 必须用确定性样本路径版本

`L = λW` 的随机版本要求**平稳性**。但真实的 SoC 流量不是平稳的：

- 帧同步流量（显示 16.67ms、摄像头 33ms）是**周期性**的
- CPU 的访存有突发性（cache miss burst）
- DMA 是大块搬运，本质上非平稳

**确定性样本路径版本在任意有限窗口成立，不需要平稳性假设**，这才是硬件建模该用的版本。

推论：**不要对帧同步流量套 Jackson 网络。** 工具应主动检测非平稳流量并警告。

### 3.2 Little's Law 是必要条件，不是充分条件

`有效带宽 ≈ 在途字节数 ÷ 延迟` 给的是**上限**，不是可达值。可达到的并发被硬件资源封顶：

- CPU 侧：MSHR 数量、line fill buffer 数量
- 链路侧：AXI outstanding 上限、ID 数量
- 互联侧：输入缓冲深度、重排缓冲深度
- 从设备侧：队列深度

一旦这些资源打满，**增加供给的负载不会提升带宽，只会提升延迟**。这正是「并发受限拐点」的成因，也是本工具最重要的诊断对象。

### 3.3 必须区分两个拐点

| | 并发受限拐点 | 器件受限拐点 |
|---|---|---|
| 成因 | 在途请求打满 outstanding / MSHR | 总线或存储核心真饱和 |
| 症状 | 延迟上升，带宽平台化，**总线存在空转** | 总线利用率接近饱和 |
| 修复 | **改配置**：加 outstanding、加 ID、加深缓冲 | **只能重新流片** |
| 代价 | 面积/延迟 | 立项决策 |

研究原话：**「报告『你在拐点上』却不区分这两者的工具是误导性的——前者便宜可移，后者是重新流片。」**

**本工具的判别方法**：在拐点处测量「总线的空转时间占比」与「队列占用率」。
- 空转占比高 + 队列未满 + 总线未饱和 → 并发受限
- 总线利用率 → 100% 或存储内部效率指标（行冲突、翻转）恶化 → 器件受限

## 4. 带宽损耗的归因框架

有效带宽不是一个数，是一个乘积：

```
BW_eff = BW_peak × η_proto × η_turnaround × η_refresh × η_row × η_arb
```

每个 η 对应一个可测量的计数器，输出为瀑布图：

```
理论峰值                     100.0%
├─ 协议开销（AXI 握手/地址相位）   -X%   计数器：握手空闲拍数
├─ 读写方向切换（turnaround）      -X%   计数器：方向切换次数 × 每次惩罚
├─ 刷新/维护开销                   -X%   计数器：tRFC/tREFI 占空比
├─ 行冲突（precharge/activate）    -X%   计数器：行缺失次数
├─ 仲裁/排队空闲                   -X%   ★ 计数器：总线空闲拍数
└─ 有效带宽                        X%
```

**倒数第二项是 PSRAM 系统最容易被忽略、通常也最大的一块。** 它代表「总线在空等，没有事务可发」——即并发不足。把它和器件饱和区分开，就是本工具的核心价值。

### 4.1 用于标定的量化锚点

| 访问模式 | 控制器效率 |
|---|---|
| 每事务开关行的读写交替（最差） | ~10% |
| 写→读同列 | ~25% |
| 长同向突发同列 | ~92% |
| 背靠背写（不含刷新） | ~100% |

其他锚点：
- 刷新直接开销 ~1.7%@100MHz（100MHz 时约 13 周期 / 7.6µs）
- tWTR/tRTW 在现代速率下可达 ~40 TCK，**等于一次完整的行命中→行失效**；同 rank 内**写→读惩罚最大**，跨 rank 几乎无惩罚
- tRC:tCK 从 SDRAM 的 9 恶化到 DDR3 的 28~39（**应作为趋势编码，不是常数**）
- 读写重排可带来最高 ~39% 的带宽增益

## 5. 失效模式的建模方法

### 5.1 死锁：静态分析优于仿真

研究证据很硬：

| 方法 | 耗时 |
|---|---|
| ECDG 静态分析（依赖图找环） | **1.28 秒** |
| 形式化方法 | 56 分钟 |
| UVM 随机验证 | **数月** |

**结论：死锁检测应该用静态分析，不是等仿真碰运气。**

本工具的方法：
1. **ECDG 三层依赖建模**：协议层 / 互联层 / 实现层（共享 FIFO、共享 credit 计数器）
2. **wait-for 图**：事务 → 阻塞它的资源 → 持有该资源的事务；环 = 死锁
3. **AXI 三类专用模式**：双路径（AW/W 分离）、环路、桥（协议转换）

**前提**：所有缓冲必须**有界且可配**。无界缓冲在数学上不可能形成依赖环，模型里也就永远检测不到死锁。

### 5.2 AXI 规范有一个洞，必须显式建模

**AMBA AXI 的 W 通道没有协议级约束**限制写主设备持有总线授权后多久才提供数据。真实的 AXI 死锁经常源于这里，而不是路由环。

本工具把「**持有授权但不给数据**」作为**一等的定时行为**建模，即主设备可以配置一个 `w_stall_profile`，模拟慢速写数据源。这不是可选的装饰，是死锁检测的必要条件。

### 5.3 饿死与优先级反转

- **饿死检测**：某主设备在 T ns 窗口内仲裁零获胜
- **优先级反转**：高优先级事务被低优先级**持有的资源**阻塞
- **公平性指标**：用 **Stall-Time Fair**（衡量被干扰拖慢多少），而不是只统计拿到多少带宽

## 6. QoS 的建模框架

### 6.1 三种契约，而不是三个优先级

来自 Arm 的方法论，这是真实设计在用的抽象：

| 契约 | 适用主设备 | 关心的量 | 失败表现 |
|---|---|---|---|
| **最小延迟契约** | CPU | 延迟 | 程序变慢 |
| **最大延迟契约** | 显示 / 摄像头 / 音频 | 延迟上界与抖动 | 可见/可听伪影、丢帧 |
| **最小带宽契约** | GPU / NPU / DMA | 带宽下限 | 吞吐不达标 |

**两层的实现结构**（对齐 Synopsys DW_axi 与 Arm）：
1. **主设备侧入口调节器**：按带宽 / outstanding 数 / 事务间隔限制贪婪流量
2. **从设备侧仲裁器**：在竞争点按优先级选谁

**必须量化的代价**：研究明确指出「**过度调节会导致内存带宽利用不足**」。这是真实 trade-off——工具应能画出「隔离度 vs 总带宽」的曲线。

### 6.2 优先级分配的非直觉规则

**CPU 放在 12~14，不要放 15。** 留出 15 给实时主设备在濒临饿死时升级使用。把 CPU 放在 15 会堵死实时保护机制。

### 6.3 仲裁器的正确性陷阱

**简单 RR 给的是每事务公平，这在 AXI 上是错的。** 16-beat burst 和 1-beat single 混跑时，burst 那路每字节只拿到 1/16 的仲裁机会。

**正确选择是 DRR（Deficit Round Robin）**：每字节公平，O(1) 处理变长包。这是很多自研模型里的隐藏 bug。

## 7. 设计空间探索（Stage 3）

### 7.1 流水线

1. **Roofline 前筛**：给每个主设备算算术强度，分类「带宽受限 / 计算受限」。**只对带宽受限的做完整 DSE**
2. **Plackett-Burman 因子筛选**：用少量实验找出哪些旋钮真的重要
3. **代理模型拟合**（响应面 / 高斯过程）
4. **Pareto 前沿细化**
5. **敏感度排序**：用 **Sobol 方差分解**，不是单旋钮 Tornado 图

### 7.2 敏感度的陷阱

**单旋钮 Tornado 图在其他旋钮变动后，排序可能反转。** Harvard 在一个 260,000 点的设计空间上验证过这一点。

推论：**不要只出一张 Tornado 图当结论。** 敏感度必须做成交互感知的（方差分解 / Sobol 指数）。

### 7.3 报告质量指标

用 **ADRS（Average Distance from Reference Set）** 衡量近似 Pareto 前沿的质量。做 DSE 就该报这个，否则无法评估「扫得够不够好」。

## 8. 学习路径的嵌入

本项目同时是学习载体。方法：

- **读到 → 实现 → 用它回答一个问题 → 写成 ADR → 术语入表**。这个循环是知识内化的唯一机制。
- **每个 bug 必须产出一个架构资产**：设计指南更新 / 验证检查项 / 模型修正
- **术语表是唯一真相源**：发现理解错误时改 `glossary.md`，不改零散笔记

### 8.1 与阶段配套的阅读（不超前）

| 阶段 | 读 | 方式 |
|---|---|---|
| 0 | AMBA AXI 规范（带问题读） | 读设计意图，不读信号定义 |
| 1 | Jacob《Memory Systems》DRAM Memory Controller + Design Analysis 两章 | 只读这两章。书老但方法论不老 |
| 1 | Harchol-Balter《Performance Modeling》 | 通读：运算定律 → M/M/1 → M/G/1 → Jackson → 均值分析 |
| 2 | Dally & Towles 第 15–20 章 | 第 17 章死锁、18–20 章仲裁与 QoS |
| 2 | Mutlu 内存调度论文（Stall-Time Fair / TCM / ATLAS） | 经 ETH 阅读清单索引 |
| 3 | Raj Jain 的测量 / 负载刻画 / 实验设计三章 | DoE 方法论原始出处 |
| 3 | Lazowska《Quantitative System Performance》（免费在线） | 性能边界技术特别适合概念阶段 |
| 长期 | Hennessy & Patterson | 通读一次后当参考。**注意它不讲片上互联 QoS** |

### 8.2 两个最高价值免费资源

- **ETH Zurich 227-2210（Onur Mutlu）阅读清单** —— 公开互联网上最好的存储系统与内存调度研究生大纲
- **CASES'12 教程 "Analytical Approaches for Performance Evaluation of NoCs"** —— 四种形式化方法（数据流分析 / 可调度性分析 / 网络演算 / 排队论）并列对比，覆盖最坏情况与平均情况

### 8.3 一个必须记住的警示案例

**Tesla HW3**。Musk 在 2026 年 Q1 财报电话会上承认 HW3「没有能力实现无监督 FSD」，原因是**内存带宽只有 HW4 的 1/8**。约 400 万辆 2019–2023 年售出的车受影响，补救方案是折价置换或电脑+摄像头改装（每车 1500–2000 美元），欧盟与澳洲有集体诉讼。

**这是公开记录里最清晰的案例：架构的内存带宽预算为最终负载设错了。而且被点名的约束不是 TOPS，是内存带宽。**

这就是本项目存在的理由。
