## 1. 背景与约束

### 1.1 为什么需要这个决策

芯片立项初期需要回答三个问题，而目前没有工具能回答：

1. **能力边界**：给定这个架构，带宽-延迟曲线的拐点在哪？能撑到什么负载？
2. **瓶颈归因**：有效带宽损耗具体花在哪里，哪一部分是**改配置能救的**，哪一部分是**必须重新流片的**？
3. **失效模式**：什么条件下出现主设备饿死、实时外设抖动、总线互锁死锁？

现状是：这些问题靠静态表格和临时脚本估算。研究结论很直接——**行业统计仅约 14% 的 ASIC/SoC 项目能一次流片成功，六个月延期可损失上亿美元**。整个架构探索阶段的正当性就来自这里。

### 1.2 目标系统

| 项 | 值 |
|---|---|
| 产品形态 | 移动/消费类 AP |
| 总线拓扑 | 单层全交叉开关 |
| 主存 | **PSRAM（硬核 IP，vendor 提供 controller + PHY，经 AXI 接入）** |
| 片上存储 | AXI SRAM |
| 主设备类别 | 计算类（CPU/GPU/NPU）、数据搬运类（DMA/存储/网络） |

### 1.3 关键约束

**约束 A —— PSRAM 是硬核，内部不可建模、也不需要建模。**

vendor 提供 controller + PHY，我们只通过 AXI 接口接入。这直接决定了建模层次：**建模它的 AXI 侧性能包络（latency vs outstanding、sustained BW、最大 outstanding、读写翻转开销），而不是内部 bank/row 时序。** 系统侧可优化的部分（outstanding 配置、仲裁、ID 分配、流量调度）作为变量去扫描。

**约束 B —— PSRAM 系统的瓶颈不在引脚带宽，在 Little's Law。**

`有效带宽 ≈ 在途字节数 ÷ 延迟`。PSRAM 延迟远高于 DDR，所以达到同样带宽所需的在途字节数成倍增加。**outstanding 不足会导致总线大量空转**——这通常比引脚带宽更早成为瓶颈。

> 例：目标 4 GB/s、空载延迟 180ns → 需在途 720 字节。若 AXI 为 64 位宽（8 字节/拍）且最大 outstanding 为 8 个 64 字节事务，则在途上限 512 字节 → **只能跑到约 2.8 GB/s，与引脚带宽无关**。

**约束 C —— 四个痛点全部在范围内。**
实时外设延迟抖动、主设备饿死/吞吐不达标、存储有效带宽不达标、总线互锁/死锁。

**约束 D —— 建模成本必须被控制。**

核心模型目标 1000~1500 行可读代码。这条来自 Keller 的 EV6 教训：他最初的性能模型膨胀到 30,000 行，被要求重写到约 1,000 行。他的结论是——**模型应该是有价值的、可理解的、明确可用的工具，不是探索想法的脚本。**

**约束 E —— 分析方法必须自证。**

架构工具的输出会用来做立项决策。没有验证机制的模型比没有模型更危险。

## 2. 候选方案

考虑过四条路线，逐条说明。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 纯 Python 自研交易级 DES** | 自建离散事件内核 + AXI 语义 + 交叉开关 + 存储包络模型 | 迭代最快；零 C++ 工具链成本；分析/可视化生态最好；有量产先例 | 无法做周期精确全芯片 | **选中** |
| B. SystemC TLM-2.0（C++） | 行业标准 TLM，socket + payload | 行业标准；可对接商业工具链；可与 RTL 协同仿真 | 价值在互操作而非快速探索；Windows 工具链本身是一个项目；样板代码量大；统计与可视化层要另做 | 排除（保留为将来移植路径） |
| C. 现有开源框架二次开发（gem5 / BookSim / Omelet / Ratatoskr） | 在其上扩展 | 有验证过的组件 | gem5 是 CPU 中心，问的是 IPC 不是总线预算；BookSim 是 NoC 专用，无 AXI/无内存控制器/无主设备模型；Omelet/Ratatoskr 是 chiplet/NoC 范畴。**都是「某一层」的工具，而本问题横跨主设备→交叉开关→存储全链路** | 排除 |
| D. 纯解析 / 表格模型 | 闭式排队论 + Excel | 瞬时出结果 | 抓不到仲裁行为、ID 重排阻塞、依赖环死锁等涌现现象 | 排除（降级为 Tier 1 前筛保留） |

### 2.1 为什么排除 B（这是最需要辩护的一条）

SystemC 的价值在**互操作与 RTL 协同仿真**，不在快速探索。而对本项目：

- **速度需求是人的迭代速度，不是机器速度。** 探索阶段要跑几百次配置，C++ 的编译-运行循环会主导工作时间。
- **分析层被低估。** 本项目一半的工作量在统计、归因、图表、扫掠——这些 Python 生态远强于 C++。
- **工具链成本。** 本机未安装 SystemC，Windows 上配置 MSVC + CMake + SystemC 是一个独立项目。
- **有量产先例支持 A。** Graphcore 在 DVCon Europe 2021 公开了纯 Python（SimPy）的 SoC 互联性能建模框架，明确用于捕捉 head-of-line blocking 和死锁，流片前后都在生产项目上使用。C2C-Explorer（DAC 2026）同样用 Python 做 AXI 互联仿真。

**保留的退路**：建模时保持事务级 + socket 式端口抽象 + 时序标注，与外设 TLM-2.0 语义对齐。若将来模型需要成为团队资产或与 RTL 协同仿真，**移植到 TLM-2.0 AT 是翻译而非重设计**。

## 3. 决策

**采用方案 A：纯 Python 3.11 自研交易级离散事件仿真内核，配置驱动，配套静态分析报告。**

- 仿真内核、统计、分析、图表：Python 3.11
- 运行环境：conda 独立环境 `socsim`（`environment.yml` 声明，可重建）
- Dashboard 前端（Stage 4）：TypeScript + ECharts
- 若将来需周期精确全芯片：Verilator + RTL，分工是「Python 扫空间，Verilator 校准点」，不在本项目范围

## 4. 取舍表

方案 A 与关键的备选 B（SystemC）对比。**数值取自本项目的实测/估算，来源已标注。**

| 维度 | A. Python DES | B. SystemC TLM-2.0 | 单位 | 数据来源 |
|---|---|---|---|---|
| 首个可用结论的时间 | 2~3 周 | 5~8 周 | 周 | 判断（含工具链搭建） |
| 单次仿真墙钟（100µs 窗口） | 秒级 | 秒级 | — | 推断，待 Stage 1 实测 |
| 仿真吞吐 | 目标 ≥1M 事件/秒 | ~1-10 MIPS | — | 领域知识，待实测 |
| 配置扫掠 100 点 | 分钟级（multiprocessing） | 小时级 | — | 判断 |
| 分析层成熟度 | numpy/scipy/matplotlib 现成 | 需自建或外接 Python | — | 事实 |
| 环境搭建成本 | 一个 `conda env create` | MSVC + CMake + SystemC，Windows 上数天 | — | 判断 |
| 与 RTL 协同仿真 | 需额外桥接 | 原生（DPI/VPI） | — | 事实 |
| 模型可交付性 | 需转换 | 行业标准，可直接交付 | — | 事实 |
| 核心代码量目标 | 1000~1500 行 | 同等功能预计 2~3 倍 | 行 | 判断 |

**取舍结论**：放弃「行业标准可交付性」与「原生 RTL 协同仿真」，换取「3 倍以上的迭代速度和显著更低的环境成本」。这个交换在**探索阶段**是正确的；如果项目目标变成「向 IP 供应商或团队交付可复用模型」，这个取舍需要重新评估（见第 6 节）。

## 5. 验证策略

架构工具必须自证，否则结论不可信。三重自校验在 Stage 1 内建：

| 校验 | 内容 | 判据 |
|---|---|---|
| **上界校验** | 达成的带宽 ≤ 理论峰值；≤ 包络 sustained BW | 任何违反即模型 bug |
| **Little's Law 校验** | 实测并发数 == 吞吐 × 延迟 | 使用**确定性样本路径版本**：任意有限窗口成立，不需平稳性假设。误差需在几个百分点内 |
| **守恒校验** | 每个从设备进出字节数严格相等 | 不相等即丢包或重复计数 |
| **已知答案测试** | 单主设备打单从设备 | 应精确达到包络的 sustained BW，且无仲裁损失 |
| **解析交叉验证** | 单服务器区间对比 M/D/1 闭式解 | 趋势一致；绝对偏差需解释 |
| **退化用例** | 1×1 交叉开关 | 零仲裁开销；零流量时零延迟 |

**额外的模型正确性机制**（来自研究，都是已知的坑）：

1. **DRR 仲裁**而非 RR——RR 给的是每事务公平，16-beat burst 对 1-beat single 时语义错误
2. **主动警示非平稳流量**——帧同步流量是周期性非平稳的，套 Jackson 网络会出错，工具应检测并警告
3. **有界缓冲**——交叉开关输入缓冲与从设备队列全部有界且可配，这是死锁可检的**前提**（无界缓冲在数学上不可能形成依赖环）

## 6. 后果

### 正面

- 2~3 周内产出第一份**可辩护**的带宽预算结论，而不是靠表格估算
- 能够区分**并发受限拐点**（改配置能救）与**器件受限拐点**（只能重流片）——这是本工具最核心的诊断能力，直接服务于立项决策
- 配置驱动 → 架构变体可枚举，为 Stage 3 的设计空间探索铺路
- 每阶段产出一份 ADR，**零额外成本积累架构师作品集**
- 全套工具链可在任意工程师的 Windows 机器上一条命令重建

### 负面（必须讲清）

- **放弃行业标准的可交付性。** 模型不能直接交给 IP 供应商或商业工具链消费。若团队需要这个能力，需按第 7 节移植。
- **无法做周期精确。** 本模型回答「架构够不够」，不回答「时序能不能收敛」。后者是 RTL 与 STA 的职责。
- **PSRAM 包络模型的精度取决于厂商数据。** 若 IP 手册只给峰值而不给 latency-vs-outstanding 曲线，模型会退化为「用峰值近似持续带宽」，此时结论可信度下降，必须显式标注。
- **不建模 PSRAM 内部。** 这是特性不是缺陷——硬核不可改，建模内部没有决策价值。但也意味着**无法回答「换一颗 PSRAM 或改控制器调度会怎样」**，那需要厂商提供不同包络。

### 需要适配的下游

- 无。这是新建项目，不改动现有设计。
- 但**产出的 ADR 会反过来约束 RTL 设计**（如 outstanding 定容、QoS 分级、缓冲深度）

### 未来可能推翻本决策的条件

1. 模型需要成为**团队共用资产**或交付给 IP 供应商 → 评估移植到 SystemC TLM-2.0 AT
2. 需要**周期精确**验证某个具体瓶颈 → 引入 Verilator 做黄金参考标定
3. 需要建模 **DDR** 而不只是 PSRAM（DDR 是自研控制器，内部可改）→ 按 DRAMSim3 的 bank 状态机 + 时序约束表方法论扩展
4. 仿真性能实测不达标（如 ms 级窗口无法在可接受时间内完成）→ 评估 PyPy、numpy 向量化或 C 扩展（**先测量后优化，不预先优化**）
