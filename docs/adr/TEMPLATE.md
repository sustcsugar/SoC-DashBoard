## 1. 背景与约束

这个决策要解决的问题是什么。**约束必须带数字**——没有数字的约束不是约束，是愿望。

要写清楚：
- 现状是什么，为什么现在必须做这个决定
- 硬约束（面积、功耗、频率、成本、进度、IP 能力边界）
- 相关的工作负载场景

> 检查点：一个不熟悉本项目的架构师读完这一节，能否理解「为什么必须做一个决定」以及「有哪些路已经被堵死了」。

## 5. 验证策略

这个决策怎么被验证是对的。分三层：

- **仿真验证**：哪些场景必须跑通，覆盖什么边界
- **断言 / 形式化**：哪些不变量必须成立（例：计数器与 IDLE 状态的关系）
- **签核标准**：WNS / TNS / 覆盖率 / 带宽达成率的具体门限

## 6. 后果

**必须写，包括负面后果。** 一个只讲好处的 ADR 不可信。

- **正面**：这个决策解锁了什么
- **负面**：接受了什么代价，哪些场景会变差
- **需要适配的下游**：哪些模块/固件/文档必须跟着改
- **未来可能需要的新 ADR**：这个决策在什么条件下会被推翻
